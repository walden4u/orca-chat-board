# 자동 답변 연구: 채점 에이전트를 믿어도 되는가

2026년 11월 14일, Windows 10, Orca 1.4.255, Claude Code 2.1.325에서 확인한 내용입니다.

## 결론

- **따로 돌리는 채점 에이전트는 쓸 만합니다.** 지금의 지시문으로 심어 둔 문제 18개를 모두 잡았고, 정상 사례 6개를 모두 통과시켰고, 시작도 하지 않은 목표 3개를 통과시키지 않았습니다. 한 번에 약 12초, 약 0.03달러가 듭니다.
- **실험을 통과한 채점자가 실제 사용에서는 틀렸습니다.** 만들지도 않은 앱에 "모두 충족"을 두 번 냈습니다. 목표와 마지막 대화가 서로 다른 일을 가리키는 경우였고, 처음 실험은 그런 경우를 다루지 않았습니다. 지시문을 고치고 그 경우를 실험에 넣었습니다.
- **그래서 채점자의 답장은 초안이고, 자동으로 보내지 않습니다.** 정상 코드에 고칠 것이 있다고 한 경우가 세 번의 실행 중 두 번 있었습니다.
- **목표는 카드가 아니라 폴더의 `GOAL.md`에 둡니다.** 계획은 Claude Code의 플랜 모드로, 실행은 `/goal`로, 확인은 채점으로 합니다. 카드에 목표를 적는 처음 설계는 실제로 써 보니 순서가 계속 어긋났습니다.

## 무엇을 물었나

"대화가 끝날 때 보낼 답장을 어떻게 만들어야 결과물이 가장 좋아지는가, 에이전트를 따로 돌려 점수를 매기는 방식은 어떤가"가 질문이었습니다. 답장이 결과물을 좋게 만들려면 일한 에이전트가 모르던 참인 정보를 담아야 합니다. "계속하시오"나 추천 문구에는 그런 정보가 없습니다. 채점 에이전트는 작업 과정을 보지 않은 채 결과물만 읽으므로 그런 정보를 낼 수 있는 후보입니다. 다만 채점자도 틀릴 수 있으므로, 쓰기 전에 정답을 아는 문제로 채점자를 먼저 시험했습니다.

채점자는 `src/judge.ts`에 있는 그대로입니다. Claude Code를 화면 없이 실행하되(`claude -p`), 읽기 도구 세 가지만 주고(`--restricted --tools Read,Grep,Glob`), 설정 파일과 훅을 읽지 않게 하고, 세션을 저장하지 않게 합니다. 목표, 마지막 요청, 에이전트의 마지막 답, 바뀐 파일을 주고, 기준별 통과 여부와 증거, "반드시 고칠 것" 목록, 판정(통과 / 고칠 것 있음 / 사람 필요)을 JSON으로 받습니다.

## 단계 0. 워커에서 실행할 수 있는가

플러그인 워커 안에서 실제로 돌려 확인했습니다. 임시 확인 코드는 지웠습니다.

| 확인한 것 | 결과 |
|---|---|
| 워커의 환경 변수 | 18개뿐. `PATH`, `USERPROFILE`, `TEMP`는 있고 `APPDATA`, `LOCALAPPDATA`, `HOME`은 없음. Orca나 Claude 관련 변수는 없음 |
| 실행 파일 찾기 | `claude.cmd` 옆의 `claude.exe`와 `git.exe`를 찾음. `.cmd`를 거치면 긴 프롬프트와 JSON 인자가 깨지므로 `.exe`를 직접 실행 |
| 로그인과 결과 형식 | 로그인된 상태로 실행됨. 정해 준 형식의 JSON 답이 `structured_output`에 담겨 나옴. 6.9초, 0.036달러 |
| Orca에 에이전트로 잡히는가 | 잡히지 않음. 실행 전, 실행 중, 실행 후 모두 Orca의 에이전트 수가 5개로 같음 |
| 금액 상한 | 아주 낮게(0.0001달러) 주면 종료 코드 1로 멈춤 |

## 단계 1. 채점자 검증

### 방법

1. 이 플러그인의 순수 함수(`sync.ts`, `board.ts`, `monitor.ts`, `cli.ts`)에 문제를 하나씩 심은 후보 44개와 정상 사례 6개를 만들었습니다. 문제는 두 종류입니다: 동작을 바꾼 것(비교 뒤집기, 경계값, 잘못된 상수)과 필요한 동작을 빼 놓은 것.
2. 후보마다 플러그인의 기존 테스트를 돌렸습니다. 44개 중 20개만 테스트에 걸렸고 24개는 걸리지 않았습니다.
3. **본 실험**은 테스트에 걸린 것만 썼습니다. 테스트가 정답 판별기이기 때문입니다. 20개 중 18개(바꾼 것 12, 빼 놓은 것 6)를 썼고 둘은 채점 전에 뺐습니다. 여기에 정상 사례 6개(손대지 않은 원본 3개, 동작이 같게 다시 쓴 것 3개)를 더해 24개입니다.
4. 채점자에게는 테스트와 git 기록을 뺀 소스 복사본, 함수별 기준 목록(3~5항목), "기준대로 구현해 달라"는 요청, "모두 구현했고 빠진 것은 없다"는 에이전트의 답, 바뀐 파일 이름을 주었습니다. 에이전트의 답은 모든 사례에서 같습니다.
5. 24개를 한 번씩 돌리고, 미리 정해 둔 6개는 한 번 더 돌렸습니다. 모델은 Sonnet(`claude-sonnet-5-5`), 노력 수준은 중간입니다.
6. 판정 규칙은 실행 전에 정했습니다. 심은 문제를 "잡았다"는 판정이 "고칠 것 있음"이고, 그 문제가 어기는 기준을 미달로 표시했을 때입니다. 정상 사례는 판정이 "통과"가 아니면 잘못된 지적으로 셉니다.
7. 통과 기준도 실행 전에 정했습니다: 놓친 결함 2개 이하, 놓친 미완성 1개 이하, 잘못된 지적 1개 이하.

실제 사용에서 틀린 통과가 나온 뒤(아래 "실제로 써 보니") **시작하지 않은 목표** 사례 3개를 더했습니다. 목표는 아무도 만들지 않은 것을 요구하고, 마지막 요청과 에이전트의 답은 이미 끝난 다른 일에 대한 것입니다. 이 사례에서는 "통과"가 곧 실패입니다.

### 결과

채점 지시문을 두 번 고쳤고, 고칠 때마다 전체를 다시 돌렸습니다.

| 지시문 | 바꾼 문제 12 | 빼 놓은 동작 6 | 정상 6 | 시작하지 않은 목표 3 |
|---|---|---|---|---|
| 처음 | 12 잡음 | 6 잡음 | 5 통과, 잘못된 지적 1 | 1 잡음, **틀린 통과 2** |
| 둘째: "목표가 판단한다"를 추가 | 12 잡음 | 6 잡음 | 5 통과, 잘못된 지적 1 | 2 잡음, 판단 보류 1 |
| 지금: 답하는 언어를 명시 | 12 잡음 | 6 잡음 | 6 통과 | 3 잡음 |

- 세 번 모두 반복한 6개는 처음과 같은 판정이었습니다.
- 시간은 중앙값 12초, 최대 20초입니다. 비용은 30회에 약 1.00달러, 1회 0.033달러입니다.
- 처음 지시문의 "시작하지 않은 목표" 결과는 나중에 그 지시문으로 돌려 본 것입니다. 실제 사용에서 난 틀린 통과가 실험에서도 그대로 재현됐습니다.
- 둘째 지시문에서는 답의 일부가 영어로 나왔습니다(33회 중 5회). 지금의 지시문에서는 33회 모두 한국어입니다.

싼 모델이 통과했으므로 더 비싼 모델은 시험하지 않았습니다.

### 잘못된 지적과 지나친 지적

- **정상 사례 `ok5`** (`cronEverySec`를 동작이 같게 다시 쓴 것). 세 번의 실행 중 두 번, 채점자는 "필드가 6개 이상인 cron 식을 null로 처리하지 않는다"며 고칠 것이 있다고 했습니다. 코드에 대한 사실은 맞습니다. 원본도 똑같이 동작합니다. 제가 쓴 기준의 "그 밖의 모양이면 null"을 문자 그대로 넓게 읽은 것입니다. 기준이 모호하면 채점자는 엄격한 쪽으로 읽을 수 있고, 같은 입력에도 실행마다 다릅니다. 마지막 실행에서 통과한 것은 고쳐진 것이 아니라 그 편차로 봐야 합니다.
- **`c1`의 반복 실행**(처음 지시문). 심은 문제는 정확히 잡았지만, "확장자를 소문자로 바꾼다"는 지적을 하나 더 붙였습니다. 의도한 동작이고 Windows에서는 문제가 되지 않습니다.

심은 문제 하나 때문에 다른 기준도 함께 어겨지는 경우에는 채점자가 그 기준들도 미달로 표시했습니다. 이것은 맞는 표시입니다.

### 참고 실험: 테스트가 잡지 못하는 문제 24개

기존 테스트에 걸리지 않은 24개도 따로 돌렸습니다(처음 지시문으로만). 이쪽은 테스트가 아니라 "제가 심었다"는 사실이 정답의 근거라서 본 실험과 분리했습니다.

| | 결과 |
|---|---|
| 동작을 바꾼 문제 12개 | 12개 잡음 |
| 빼 놓은 동작 12개 | 12개 잡음 |
| 시간 | 중앙값 13초, 최대 19초 |
| 비용 | 24회에 0.90달러, 1회 0.037달러 |

테스트가 닿지 않는 곳에서도 채점자가 문제를 찾았다는 뜻이고, 지금의 테스트에 빈 곳이 24군데 있다는 뜻이기도 합니다. 목록은 `docs/auto-reply-research/pool.mjs`의 `EXTRA`에 있습니다.

## 실제로 써 보니

처음에는 카드에 목표를 적고, 대화의 창에서 채점하게 만들었습니다. 같은 날 실제로 써 보면서 세 가지가 드러났습니다.

1. **목표가 에이전트에게 전달되지 않았습니다.** 카드에 적은 목표는 채점의 기준일 뿐이어서, 따로 대화에 보내야 했습니다. 보내지 않은 채 채점하니 시키지도 않은 일에 "고칠 것"이 나왔습니다.
2. **틀린 통과가 났습니다.** 카드의 목표를 "phoenix로 간단한 투두앱"으로 바꾸고 채점하자, 채점자는 "요청한 것이 모두 충족됐습니다"라고 두 번 답했습니다. 폴더에는 그런 앱이 없었습니다. 채점자가 받은 마지막 요청과 에이전트의 답은 그 전의 다른 일(이미 끝난 일)에 대한 것이었고, 채점자는 그 일만 확인했습니다.
3. **보드가 추측할 것이 계속 늘었습니다.** 목표를 보냈는지, 이 턴이 어느 목표의 일인지, 이 채점이 어느 목표의 것인지. 고칠수록 규칙이 늘었습니다.

뿌리는 하나였습니다. 목표가 에이전트가 볼 수 없는 곳(카드)에 있었습니다. 그래서 이렇게 바꿨습니다.

- **목표는 그 대화 폴더의 `GOAL.md`에 둡니다.** 에이전트가 쓰고 체크하는 목록입니다. 에이전트, 사용자, 채점자가 같은 파일을 보고, 보드는 체크 상자를 세어 "목표 3/5"를 보여 줄 뿐 아무것도 기억하지 않습니다.
- **채점 지시문에 "목표가 판단한다"를 넣었습니다.** 마지막 요청은 맥락이고, 마지막 요청에는 답했어도 목표의 항목이 남아 있으면 통과가 아닙니다. 체크된 상자는 에이전트의 주장이지 증거가 아닙니다.
- **이 경우를 실험에 넣었습니다**(위 표의 마지막 열).

## 플랜 모드와 `/goal`을 쓰는 흐름

목표를 세부 항목으로 나누는 일과 끝까지 실행하는 일은 Claude Code에 이미 있는 기능에 맡겼습니다. 임시 Claude 세션(Sonnet)에 버튼이 보내는 문구를 그대로 보내 확인했습니다.

| 단계 | 보낸 것 | 실제로 일어난 일 |
|---|---|---|
| 계획 | "플랜 모드로 들어가서 다음 목표의 계획을 세워 주세요…" | 에이전트가 스스로 플랜 모드에 들어가 살펴보고 계획을 씀. 터미널에 승인 창이 뜨고, 승인 전에는 아무것도 바뀌지 않음 |
| 승인 뒤 | (터미널에서 승인) | `GOAL.md`에 확인 방법이 붙은 6개 항목을 쓰고, 위에서부터 진행하며 체크. 60초 안에 6개 모두 체크, 테스트 통과 |
| 실행 | `/goal GOAL.md의 모든 항목이 체크되어 있고…` | 항목이 2/6, 4/6, 6/6으로 체크되고 "Goal achieved"로 스스로 끝남 |

플랜 모드 없이 "체크 목록만 써라"고 시키는 방식도 시험했고 동작했습니다. 다만 플랜 모드 쪽이 먼저 코드를 살펴보고 설계 결정과 경계 사례까지 적어서 계획이 더 좋았고, 승인 전에는 파일을 바꿀 수 없다는 것이 지켜집니다. 대신 승인은 보드가 아니라 대화(터미널)에서 해야 합니다.

여러 줄로 된 글이 대화에 하나의 메시지로 들어가는 것도 같은 방법으로 확인했습니다.

## 한계

- **쉬운 조건입니다.** 작은 순수 함수에 문제 하나, 번호 붙은 분명한 기준입니다. 실제 일은 변경이 크고 목표가 덜 분명합니다.
- **표본이 작습니다.** 정상 사례가 6개, 시작하지 않은 목표가 3개뿐입니다. 비율은 대략적인 값입니다.
- **문제를 만든 쪽과 찾은 쪽이 같은 계열의 모델입니다.**
- **실험이 다루지 않은 경우가 또 있을 것입니다.** 틀린 통과는 실험 밖에서 나왔습니다. 지금의 사례들도 제가 떠올린 경우일 뿐입니다.
- **재지 않은 것**: 채점 결과로 답장을 보냈을 때 최종 결과물이 실제로 좋아지는지, 문서 작업에서는 어떤지, 다른 모델은 어떤지, `/goal`이 도는 동안 보드의 상태 표시가 어떻게 보이는지.
- **채점자는 읽기만 합니다.** 테스트나 프로그램을 돌려 보지 못합니다. `/goal`의 확인은 반대로 대화에 적힌 말만 봅니다. 둘 다 에이전트가 체크만 하고 끝내지 않은 경우를 완전히 막지는 못합니다.

## 플러그인에 반영한 것

모두 설정 **"목표 모드"**(기본 꺼짐) 뒤에 있습니다. 꺼져 있으면 아무것도 보이지 않고 아무것도 돌지 않습니다.

- 대화의 창(카드를 클릭하면 열리는 창)에 버튼 세 개: **목표 계획**(플랜 모드로 계획, 대화에서 승인, `GOAL.md` 작성 후 진행), **목표 실행**(`/goal`), **채점**.
- 카드에 **목표 3/5**처럼 `GOAL.md`의 진행을 보여 주고, 창에는 항목 목록을 보여 줍니다.
- 채점 결과는 창에 **채점표**(기준별 통과 여부와 증거, 고칠 것, 시간과 비용)로 나오고, 고칠 것이 있으면 **답장 초안**이 입력 칸에 들어옵니다. Enter로 그대로 보내거나 고쳐서 보냅니다. 초안에는 "틀린 지적이면 고치지 말고 이유를 답하라"는 문장이 붙습니다.
- 채점자에게는 `GOAL.md`, 마지막 요청, 에이전트의 마지막 답과 함께 git의 변경 내역을 줍니다. `GOAL.md`를 추가한 커밋이 기준점입니다.
- 채점 모델은 이 실험을 통과한 Sonnet, 중간 노력 수준입니다. 1회 상한은 0.5달러, 5분입니다.
- 어떤 답장도 자동으로 나가지 않습니다. 초안을 그대로 보냈는지, 고쳤는지, 쓰지 않았는지를 카드마다 셉니다. "쓰지 않음"은 초안을 두고 대화가 다음 턴으로 넘어갔을 때만 셉니다. 처음에는 채점을 다시 누를 때도 세었는데, 그러면 다시 채점한 횟수만큼 수치가 부풀었습니다.
- 카드에 검증 명령(예: `mix test`)을 적어 두면 플러그인이 채점 전에 그 폴더에서 실행하고, 종료 코드와 출력의 끝을 채점자에게 줍니다. 채점자가 실행할 수 없다는 한계를 메우려는 것입니다. 이 부분은 위 실험에 들어 있지 않습니다. 실험의 사례는 검증 명령 없이 채점했고, 명령이 없을 때의 지시문은 실험 때와 같습니다.

- 틀린 통과나 잘못된 지적을 만나면 그 경우를 `pool.mjs`에 사례로 넣고 실험을 다시 돌립니다. 이번의 "시작하지 않은 목표"가 그렇게 들어온 사례입니다.
- 채점 모델이나 지시문을 바꿀 때도 아래 방법으로 다시 돌려 확인합니다.

## 다시 돌리는 법

사례, 실행 스크립트, 채점표 원문이 `docs/auto-reply-research/`에 있습니다.

```sh
node docs/auto-reply-research/experiment.mjs setup            # 사례를 만든 소스(커밋 5f5e555)를 임시 폴더에 복사
node docs/auto-reply-research/experiment.mjs prep             # 사례마다 기존 테스트 실행 (Orca 필요, 사례당 약 8초)
node docs/auto-reply-research/experiment.mjs run main 1       # 본 실험 24회 (Claude Code 로그인과 사용량을 씀)
node docs/auto-reply-research/experiment.mjs run main 2 s2 m6 s9 c1 ok1 ok4   # 반복 6회
node docs/auto-reply-research/experiment.mjs run unstarted 1  # 시작하지 않은 목표 3회
node docs/auto-reply-research/experiment.mjs run extra 1      # 참고 실험 24회
node docs/auto-reply-research/experiment.mjs score main --md  # 집계. 새 실행 결과가 없으면 보관된 결과를 집계
```

- `pool.mjs`: 사례 전부(무엇을 무엇으로 바꿨는지, 어느 기준을 어기는지)와 함수별 기준 목록.
- `results/`: 실행마다 채점자가 낸 채점표 원문, 시간, 비용. `main.json`과 `unstarted.json`이 지금의 지시문, `main-second.json`과 `unstarted-second.json`이 둘째 지시문, `main-first.json`, `unstarted-before.json`, `extra.json`이 처음 지시문의 결과입니다.
- 다른 지시문과 비교하려면 `JUDGE_MODULE`에 그 버전의 `judge.ts` 파일 URL을 줍니다.
